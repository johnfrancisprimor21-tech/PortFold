# PortFold Prototype, Bug, and Learning Log

This retrospective gathers design decisions, reported problems, and lessons from prototyping. Exact dates were not consistently recorded, so entries are ordered by project stage. It distinguishes what the user observed from what the code/schema inspection confirms. A report is not treated as a reproduced defect unless there is a recorded reproduction.

## Deletion behavior and operational note

Move-to-Trash sets `portfolios.deleted_at`, keeps child rows and image files, and removes the portfolio from active management and public lookup. Restore clears `deleted_at`. Permanent deletion is restricted to the authenticated owner and to trashed records; it removes rows from `skills`, `projects`, `education`, `experiences`, `links`, `github_stats`, `portfolio_info`, and `portfolios`. Image URLs are gathered from the profile photo and both project image columns, and URLs referenced elsewhere are excluded from deletion. Storage removal and PostgreSQL changes cannot be committed as one atomic transaction; after a partial Storage failure, some image objects may already be gone while the record remains in Trash for a retry.

## Evidence and release follow-up

The screenshots in `screenshots/` are synthetic examples. The raw screenshots of a personal portfolio, router administration, firewall settings, and local network diagnostics are not copied into GitHub because they contain personal or network details. User-reported failures remain labeled as reports until a safe reproduction confirms them.

Open follow-up items are tracked in `QA-CHECKLIST.md`: complete mobile/readability and assistive-input checks; verify password reset, OAuth, email delivery, and HTML export; exercise create/edit/restore/permanent-delete against disposable data; and add a reproducible baseline schema for a fresh Supabase project.
